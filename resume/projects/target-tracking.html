INDEPENDENT TECHNICAL PROJECT · REINFORCEMENT LEARNING

Reinforcement Learning-Based Autonomous Target Tracking

A real-time PPO-based tracking controller combining custom simulation, state estimation, reward engineering, and low-latency TCP communication.

Python PyTorch Gymnasium Stable-Baselines3 PPO TCP/IP

1. Project Overview

This project explores the application of Reinforcement Learning (RL) to real-time autonomous target tracking. The objective is to train an intelligent agent to follow a continuously moving target through environmental interaction rather than relying on manually programmed tracking rules.

A custom Gymnasium-based reinforcement learning environment was developed using Python, with Proximal Policy Optimization (PPO) as the learning algorithm. The system connects the learning controller to an external 2D target-tracking application through a TCP communication interface.

The Green dot moves independently within the simulation, while the Blue dot acts as the controlled agent. The PPO controller continuously observes the environment, generates movement commands, and adjusts the follower's position to minimise tracking error while maintaining smooth movement.

An important part of the project involved investigating the external application's communication behaviour and designing the RL environment around its actual data and timing constraints.

2. Simulation Environment

The environment represents a dynamic two-dimensional target-tracking problem with two primary entities:

  • Green Dot – Target: Moves independently and creates a continuously changing tracking objective.
  • Blue Dot – Agent: The controlled entity whose movement is determined by the PPO policy.
  • Environment: Manages observations, movement commands, state estimation, reward calculation, and communication with the application.

The agent must continuously respond to changes in the target's position. This creates a closed-loop learning problem in which each action influences the next environmental state.

3. TCP Communication and System Identification

A TCP client-server interface was implemented to exchange environmental observations and movement commands with the external application.

Incoming Telemetry – 20 Bytes per Packet

  • Green dot X and Y coordinates: 2 × int32 (8 bytes).
  • Blue dot X and Y tracking-error magnitudes: 2 × int32 (8 bytes).
  • X and Y error flags: 2 Boolean values (2 bytes).
  • Carriage return and line feed terminators (2 bytes).

System-identification finding: The secondary coordinate fields initially appeared to represent the Blue dot's coordinates. However, packet-level investigation revealed that they represented unsigned absolute tracking-error magnitudes: |Green X − Blue X| and |Green Y − Blue Y|.

Since absolute error values do not preserve directional information, treating them as raw coordinates caused incorrect tracking behaviour and direction reversals. This required reconstructing the Blue dot's internal position from previously commanded coordinates.

Outgoing Commands

  • Position Mode (P) – 13 bytes: Sends the Blue dot's commanded X and Y positions using two int32 values and protocol delimiters.
  • Configuration Mode (C) – 17 bytes: Adjusts object speed and object size through configuration parameters.

Packet diagnostics also identified a deterministic application update interval of approximately 15 ms (66.7 Hz). Synchronising RL interactions with incoming telemetry helped eliminate socket backlog bursts and timing inconsistencies.

4. Observation Space and Action Design

A custom Markov Decision Process (MDP) was formulated using a 13-dimensional observation space and a 2-dimensional continuous action space.

Input – 13-Dimensional Observation Space

  • Green target position: X and Y coordinates (2).
  • Signed tracking error: X and Y relative errors (2).
  • Estimated Green and Blue velocities: X and Y components (4).
  • Velocity-estimation validity flags (2).
  • Current application speed setting (1).
  • Previous movement action: X and Y components (2).

The observation features are normalised into a bounded range of [-1, 1]. Tracking errors use a scaling parameter of 80 pixels to improve sensitivity near the target.

Output – 2-Dimensional Continuous Action Space

The PPO policy generates two continuous action values, corresponding to the Blue dot's X and Y movement. Each action is converted into a bounded position increment, with a maximum movement step of 12 pixels per interaction.

Previous-action information is retained in the state representation so that the reward function can account for abrupt changes in consecutive movements.

5. PPO-Based Learning Architecture

Proximal Policy Optimization (PPO), implemented through Stable-Baselines3, was used to train the agent's continuous tracking policy.

The closed-loop learning process follows these steps:

  1. The agent receives the current 13-dimensional observation.
  2. The PPO policy generates a continuous 2D action.
  3. The action is converted into a position command.
  4. The command is transmitted through TCP.
  5. The application updates the Blue dot and returns new telemetry.
  6. The environment reconstructs the updated state and calculates the reward.
  7. Collected interaction experience is used for PPO policy optimisation.

Reward Engineering

  • Distance Penalty: Encourages minimising the target-tracking distance.
  • Progress Reward: Rewards improvements in tracking distance between steps.
  • Jerk Penalty: Discourages abrupt changes between consecutive actions.
  • Closeness Reward: Provides continuous positive reinforcement while the agent remains within a 5-pixel tracking zone.
  • Out-of-Zone Penalty: Penalises time spent outside the desired tracking threshold.

This reward design encourages the agent not only to reach the target but also to maintain stable tracking behaviour.

6. Engineering Challenges and Improvements

Initial closed-loop experiments revealed unexpected oscillations, coordinate discontinuities, and timing inconsistencies. These issues required investigation beyond the reinforcement learning algorithm itself.

State Reconstruction

The incoming application telemetry provided unsigned tracking-error magnitudes rather than signed Blue dot coordinates. To address this ambiguity, I implemented history-based internal state tracking using previously commanded Blue coordinates.

Observation and Reward Conditioning

  • Added previous-action information to the observation space to support smoother movement.
  • Tightened tracking-error normalisation from 500 to 80 pixels to improve sensitivity near the target.
  • Introduced continuous closeness reinforcement within the 5-pixel target zone to reduce post-arrival drift.
  • Synchronised RL interactions with incoming telemetry to maintain consistent timing.

These changes were evaluated through successive policy versions rather than treating the initial PPO configuration as a final solution.

8. Research Motivation and Future Direction

This project strengthened my interest in a broader reinforcement learning challenge: the dependence of conventional RL algorithms on manually predefined observation spaces.

The current controller uses a manually designed 13-dimensional observation vector. This raised a fundamental research question for me: can an intelligent agent autonomously discover meaningful state representations from environmental information rather than relying entirely on manually selected features?

My proposed research direction is Autonomous State-Space Discovery and Explainable Representation Learning for Reinforcement Learning. I am particularly interested in investigating reward-aware feature discovery, compact state representations, and interpretable policy learning.

In the longer term, I hope to investigate how these approaches can improve adaptive decision-making in dynamic physical environments and autonomous robotic systems.
